# ClearLedger: Track 04 technical and product review

Review date: 5 September 2026. Reviewed baseline: [`36794ac`](https://github.com/pankajbaid567/ClearLedger/commit/36794ac3262c651a93da17a1fabf13449d2bee1e). This is an assessment of the supplied implementation, with independently reproduced findings and an implementation roadmap. Recommendations below are not implemented fixes.

**Verdict: the product direction fits Track 04 well, but the current implementation is not submission-ready.** It already has a substantial reconciliation pipeline, a usable finance interface, a 693-row synthetic batch, an evaluator, and an exception queue. However, financial correctness, evaluation validity, truthfulness of displayed claims, and clean-clone startup need repair before adding features. Passing the supplied benchmark currently provides insufficient assurance: targeted corruptions pass the financial checks, and the evaluator misses several kinds of wrong predictions.

The strongest positioning is: **“ClearLedger closes a payment-to-bank reconciliation batch, proves every accepted allocation, and routes every unresolved amount with evidence and a next action.”** Make that one loop excellent. Forecasting and tax features should support it only when their results have an equally defensible evidence trail. Competitive quality can be improved substantially; no review can guarantee a hiring outcome or an unbeatable project.

## Submission blockers, in priority order

### 1. Remove synthetic scenario information from financial decisions

**P0 — confirmed by a rename-only reproduction.** `services/reconciliation/exceptions.py:82` and `:139` classify timing cases from `SET_T` prefixes; the classifier discards the supplied policy. `orchestrator.py:238` and `:263` also zero residuals using that prefix.

Renaming `SET_T0031` consistently across the source records, without changing amounts or dates, changes its state from `PENDING_WITHIN_SLA` to an actionable missing-bank exception and changes its cash bucket. An opaque identifier must not alter financial meaning. This is leakage through synthetic naming conventions even though the engine does not read the private truth file.

**Fix:** derive SLA from explicit capture/settlement timestamps, bank receipt evidence, versioned policy, time zone, holidays and a recorded `as_of` instant. Use opaque entity identifiers. Keep scenario labels exclusively in evaluation truth. Add a metamorphic test asserting that bijective renaming of every ID preserves normalized relationships, states, amounts and cash.

**Acceptance:** rename-only, shuffled-row and alternate-seed batches give semantically identical results; changing the `as_of` instant across an actual SLA deadline changes only the appropriate timing decisions.

### 2. Make financial proof complete before declaring a case reconciled

**P0 — multiple corruptions reproduced.** In a batched case, increasing one order by 1,000 paise or changing its merchant drops an order-payment relationship but still yields `RECONCILED` with all recorded invariants passing. Increasing a payment settlement component by 1,000 paise together with settlement net and bank amount also passes, despite settlement credit exceeding capture. A `failed` settlement and an explicitly conflicting bank UTR can also be accepted in isolated probes.

The central weakness is that correctness checks on the surviving edges do not prove that all required relationships exist. A balancing subset is insufficient proof of a complete lifecycle.

**Fix:** define per-entity obligations and verify coverage as well as arithmetic: merchant/currency consistency for every relevant row; all captured payments accounted for; every required order link present or explicitly excepted; allocations bounded by capture and component values; no bank credit consumed twice; status eligibility; and explicit identifier conflicts that cannot be bypassed by a weaker fallback. Distinguish missing identifiers from contradictory identifiers.

**Acceptance:** each reproduction becomes an explicit exception with the broken obligation named. Every `RECONCILED` case has a complete, independently checkable proof, including row coverage and allocation conservation.

### 3. Repair the evaluator so wrong predictions cannot score perfectly

**P0 — reproduced.** `evaluator/metrics.py:15` compares relationship IDs/types while ignoring allocated amounts and currency. Setting every predicted allocation to zero and corrupting predicted gross/net amounts leaves the current metrics unchanged. Duplicating every prediction produces case accuracy **2.0** and monetary reconciliation rate **1.5284**. An unknown extra reconciled case adds no false-positive case to the current count.

The CLI accepts an empty prediction report with the wrong dataset ID, one billion claimed rows and a microsecond duration, then exits successfully with “All safety checks passed.” Its separate recall output is zero and hidden-case count is 75, so the success gate is materially incomplete. The API has an additional dataset check; do not generalize the CLI flaw to every endpoint.

**Fix:** reject duplicate or unknown case IDs, duplicate/unexpected edges, missing required cases, inconsistent dataset checksums and invalid monetary values before scoring. Score allocated amount and currency correctness separately from topology. Calculate money coverage from financially correct predictions. Bind the report to source manifest, policy, engine commit and evaluator version. Gate recall, coverage and completeness as well as precision. Treat zero evaluated samples as “not evaluated” in the product.

**Acceptance:** corrupting any amount/currency lowers the appropriate metric or invalidates the report; every bounded rate stays within [0,1]; empty and wrong-dataset reports fail; unknown accepted predictions count as unsafe output. Independent evaluator mutation tests should run in CI.

### 4. Correct cash and forecasting semantics

**P0 — source and numeric reproduction.** `services/cash_position/service.py:72` subtracts refund/dispute/reserve components from settlement net values that already include those deductions. For the demo, deductions of **₹22,201.85** are subtracted again. The returned `safe_cash_paise` also includes **₹11,194.39** in transit.

The forecast then uses that value as opening cash and adds the in-transit amount again (`forecast.py:149`; cash route `:85`). Its observed starting cash is ₹1,33,512.19 and projected ending cash ₹1,44,706.58, adding ₹11,194.39 that was already represented in the baseline formula. Multiple incorrect effects can partially offset; a plausible final amount is not evidence of correctness.

The default forecast calls **4 August 2026 “Today”** during this 5 September review. Confidence values are fixed constants, daily future deductions are always zero, and a constructed Sunday receipt is credited on the non-banking date with confidence 1.0. The API does not pass the run's policy to forecast or tax calculations.

**Fix:** define a signed movement ledger and ensure each movement contributes once. Separate confirmed batch receipts, available bank balance (only when an opening balance/account statement supports that claim), in-transit receivables, expected receivables and future obligations. Carry unapplied future adjustments with status and due date; do not deduct historical settled components again. Start forecasts from confirmed opening liquidity and add future net receipts once. Record an explicit as-of time; label historical demonstrations as scenarios. Use policy-aware landing dates. Replace invented probabilities with evidence categories until calibrated against outcomes.

**Acceptance:** settled refund, future refund, reserve release, negative settlement, split settlement, holiday and overdue examples each have independently specified expected balances. Moving one receipt from transit to confirmed conserves total recognized money and never creates a second receipt. API and pure-function forecasts agree.

### 5. Scope every case read and action to its run

**P0 — reproduced against isolated database rows.** Case IDs repeat across runs, but case routes look up a bare `case_id`. `CaseRepository.get_case` chooses the newest matching row. Opening an older run after a second demo can retrieve the newer case; rejecting it updates the newer run.

**Fix:** use `/runs/{run_id}/cases/{case_id}` or immutable case-row UUIDs everywhere: details, evidence, candidates, review, Q&A citations, exports and React Query keys. Enforce run membership in the database access layer. Use run-scoped foreign keys for decisions and tasks.

**Acceptance:** create two runs with the same business case ID, then read and modify each independently. Neither values, audit history nor cash in the other run changes. Invalid run/case combinations return 404.

### 6. Derive every displayed claim from evidence

**P0 — source-confirmed, including visible badges.** `ClaimsLedgerModal.tsx` hardcodes passing claims and perfect scenario results. “10/10 Verified” appears regardless of whether a run was evaluated. Q&A defaults missing precision/recall/F1 to 1.0 and can render actual precision 0.7 alongside “100.0%,” or three false positives alongside “Zero false matches.” A pending case with no bank edge can display a zero bank credit as “Matched” because the equation UI uses zero residual as its success test.

**Fix:** use `NOT_EVALUATED`, `RUNNING`, `PASSED`, `FAILED`, `UNAVAILABLE` and `STALE` states derived from a versioned backend report. Include numerator, denominator, dataset/checksum and measurement time. Separate demo reference values from current-run evidence. Render missing bank data as absent, never numeric zero with a success badge. Show AI disabled, attempted, completed, fallback and rejected-output states from actual execution metadata; a configured model name does not mean AI ran.

**Acceptance:** an empty run, custom upload, failed evaluation and deliberately degraded score produce no success badge. No metric disagrees across overview, claim panel, Q&A and exports. A pending receipt remains visibly unverified even when the settlement equation balances.

### 7. Restore clean-clone startup and manual upload

**P0 — executed failures.** `apps/api/app/routes/runs.py:142` references undefined `settings`; its oversized-file branch also references undefined `APIError` and supplies the wrong positional constructor signature. The manual upload lifecycle cannot work reliably. The demo path bypasses that route, explaining why the demo can pass while upload tests fail.

`prompts/exception_analyst.v1.md` and `prompts/grounded_qa.v1.md` are missing. Several AI tests fail on these missing files; API Docker COPY also fails. The clean build additionally expects gitignored `evaluator_private/`.

**Fix:** restore versioned prompt assets and validate them at startup for enabled features. Repair upload configuration and structured 413 handling; share one bounded ingestion path for demo and manual files. Generate synthetic evaluator truth explicitly in a demo/evaluator setup step. Keep a normal product runtime separate from evaluator truth. Run all setup instructions in a fresh checkout with no preexisting `.env`, database or ignored files.

**Acceptance:** clean install and Docker startup succeed; five manual CSVs complete the same loop as demo; oversized files yield 413; AI-off works without credentials; mocked failure tests and prompt contracts pass.

### 8. Enforce grounding on AI output, not just its citation list

**P1 — reproduced with a mocked provider.** The Q&A service accepts an invented cash amount and `CASE_INVENTED` in answer text, filters the invalid citation list to empty, and still returns the unvalidated text. The response path advertises grounding. User questions are also interpolated into the system prompt template rather than kept solely as lower-trust input.

**Fix:** have the model return typed intents, explanation fragments and references to approved fact IDs. Resolve every numeric claim and entity ID from server-owned facts; reject or fall back on unsupported claims. Keep user questions and source narrations in explicit untrusted fields. Mark deterministic templates and live-model interpretation separately. Preserve the existing boundary that the model cannot authorize money or declare reconciliation.

**Acceptance:** invented amounts, unknown IDs, altered currency, contradictory summaries and prompt-injection text trigger a truthful refusal/fallback. Record validation results and provide citations to the exact run/case/evidence, not a loosely related case list.

### 9. Serialize review actions before recomputing run totals

**P0 — reproduced under a controlled concurrent schedule.** Two independent review transactions approve cases worth 100 and 200 paise. Both cases finish `RECONCILED`, but the persisted bank-confirmed aggregate is **100 instead of 300 paise**, and run metrics show only one reconciled case. The reproduction uses isolated synthetic database rows and barriers to expose the interleaving; it does not change the application's computed amounts.

`services/reconciliation/review_service.py:433` recalculates aggregates from a case snapshot without first serializing mutations on the run. Each transaction can read the other case before its approval commits and overwrite the aggregate with stale values.

**Fix:** acquire the run lock before reading/modifying the case and recomputing aggregates; use case versions to reject stale operator actions. Bind reverification to the run's recorded policy, not the mutable default policy. A larger event/projector design is optional; a correct transaction boundary is sufficient for this project.

**Acceptance:** simultaneous approvals, approve/reject and review/rerun tests leave cash and state counts identical to a fresh independent recomputation. Conflicting stale actions return an explicit conflict instead of silently losing an update.

## Additions that would make this stand out

### A. A demonstrated exception-to-resolution loop

This is the highest-value product addition after correctness fixes. Start with a missing bank receipt, show the exact missing evidence and amount, assign an owner, ingest a late synthetic bank row, reverify, update cash, close the task and export the decision history. Preserve the first run and show a second execution linked to it. An unresolved ambiguous case should remain unresolved alongside the resolved one.

The receipt should show old state → new state, new evidence IDs, checks rerun, changed money buckets, remaining exceptions and actor. This directly proves that the system closes finance work rather than merely producing a dashboard. Define closure as a completed reconciliation control package; real ledger posting is not necessary to meet this chosen loop.

### B. An independent challenge batch

Use a separate generator or independently authored fixtures with opaque IDs, unfamiliar narration, changed policies, missing rows and contradictory evidence. Predeclare development, validation and sealed challenge splits. Publish per-scenario results, not just an aggregate. Changing only a seed in the same scenario-coded generator is inadequate evidence of generalization.

Include many-to-many settlements, partial refunds across periods, duplicate delivery, shared amounts/UTRs, chargeback reversal, reserve release, failed/reversed settlements, cutoff boundaries, holidays, malformed currency/amounts, orphan bank credits and disconnected payment records. Label supported cases and intentional abstentions. Track unsafe accepted amount as well as unsafe accepted case count.

### C. A small independently verifiable reconciliation receipt

Export source hashes, policy/calendar hash, engine/evaluator versions, as-of time, row coverage, accepted allocations, residuals, exception register and decisions as a machine-readable bundle. Provide a small verifier that checks the arithmetic and coverage without the API server or LLM. A checksum establishes integrity relative to an expected hash; it does not by itself establish correctness or prevent a privileged actor from rewriting both data and hash.

### D. A Razorpay-shaped read-only adapter

Your five-file canonical model is a useful internal representation. Add a deterministic adapter for synthetic data shaped like Razorpay's settlement recon response. Razorpay documents payments, refunds, transfers and adjustments in the recon endpoint, including settlement IDs and UTR fields. Preserve the original entity and debit/credit semantics, pagination provenance, fees, tax and hold state. This makes the product easier for Razorpay reviewers to map to actual workflows. [Razorpay settlement recon documentation](https://razorpay.com/docs/api/settlements/fetch-recon/)

Keep “processed settlement” separate from bank-confirmed cash: Razorpay's webhook documentation warns that processed status does not by itself mean funds are credited. Require bank-side evidence before promoting the receipt to confirmed. A signed, idempotent webhook replay using synthetic payloads is a useful later extension. [Razorpay settlement webhook documentation](https://razorpay.com/docs/webhooks/settlements/)

### E. Measurable AI assistance

After restoring prompts and grounding, evaluate the analyst on a labeled exception set. Measure next-action accuracy, valid evidence citation rate, unsupported-claim rate, appropriate abstention, p50/p95 answer time, provider attempts/tokens, and actual priced cost or “cost unavailable.” Compare deterministic templates, deterministic plus AI, and unaided human review on the same tasks. Report measured review time only after conducting the experiment.

The useful agent loop is bounded: inspect case → retrieve allowed evidence → propose a next action/candidate → invoke deterministic verifier → either produce a supported recommendation or abstain → queue a task. Automatic authoritative financial decisions still require complete deterministic proof. Do not add an LLM-only matching baseline merely to manufacture a dramatic comparison.

### F. A compact finance control room

The first screen after a run should answer five questions immediately: how much was processed, how many cases were reconciled, what accuracy was actually evaluated, how much remains unresolved, and what the next action is. Show 75 cases / 693 rows; 53/75 auto-reconciled; evaluated precision with its denominator and scope; 15 exceptions plus seven pending; confirmed receipts and unresolved exposure separately. Every number should open its contributing rows.

Keep the existing clear typography, restrained color and money formatting. Add keyboard-accessible evidence navigation, focus management for dialogs, clear empty/error states and one concise next-action column. Reduce repeated “verified” badges and move secondary analytics behind evidence-backed sections.

## Submission acceptance checklist

- A clean clone installs, migrates, builds and runs without private local artifacts.
- Demo and custom uploads both complete; unknown ground truth is shown as unavailable.
- All data-dependent decisions survive opaque ID renaming and row-order changes.
- No unsafe reconciliation in the regression/challenge corpus; uncertainty remains explicit.
- Every accepted allocation has correct amount, currency, identity and complete row coverage.
- Cash reconciles to unique signed movements; in-transit receipts and adjustments are counted once.
- Evaluator rejects corrupt, duplicate, incomplete and mismatched prediction reports.
- Match rate, accuracy, coverage, exceptions and throughput have explicit denominators and scope.
- Empty or failed evaluations never display a verified badge or perfect QA answer.
- Case reads/actions are isolated by run; review history survives versioned reprocessing.
- AI returns only supported claims or a clearly labeled fallback, with measured usefulness.
- At least one late-evidence exception resolves end to end and another honest exception remains open.
- All nine browser tests and the corrected Python suite pass; CI retains evidence artifacts.
- README, exports, video, backup and dashboard agree on the same measured release.

The existing project is substantial enough to improve rather than replace. Its strongest differentiator will be the ability to survive a reviewer deliberately trying to break its financial proof, and to explain precisely what remains unresolved.
